Depurando com -v

O -v transforma um erro misterioso numa lista de passos. Esta aula ensina a ler.

Você vai aprender
  • Ler as linhas do ssh -v.
  • Filtrar com 2>&1 | grep.
  • Saber onde a conexão parou.

Todas as saídas desta aula foram colhidas de verdade com o OpenSSH 10.0p2 no Linux (Debian 13, Bash 5.2, pt_BR.UTF-8), no laboratório do guia: o notebook (usuária ana, 192.168.0.10), o servidor (usuário lab, 192.168.0.20) e o interno (192.168.0.130, que só o servidor alcança). Antes de cada caixa o laboratório volta a um estado conhecido. As chaves e as impressões digitais que aparecem são de teste e já foram destruídas.

O ssh fala o que está fazendo

Quando algo dá errado e a mensagem final não ajuda, rode o mesmo comando com -v (de verbose). Cada linha que começa com debug1: é um passo da conexão. -vv e -vvv mostram ainda mais.

A saída completa tem dezenas de linhas, e as mensagens do -v saem pela saída de erro. Por isso o 2>&1 antes do grep:

1. Uma conexão que deu certo

$ ssh -v lab@servidor true 2>&1 | grep -E 'Connecting to|Connection established|Authenticating to|is known and matches|Authentications that|Offering|accepts key|Authenticated to'
debug1: Connecting to servidor [192.168.0.20] port 22.   « 1. achou o IP e a porta
debug1: Connection established.
debug1: Authenticating to servidor:22 as 'lab'
debug1: Host 'servidor' is known and matches the ED25519 host key.   « 2. a chave do servidor confere
debug1: Authentications that can continue: publickey,password   « 3. o que o servidor aceita
debug1: Offering public key: /home/ana/.ssh/id_ed25519 ED25519 SHA256:1wgPtPehvxJHxq1qIDo4s7Eu1nZObhihxhAUBwbUHkU   « 4. o notebook oferece a chave
debug1: Server accepts key: /home/ana/.ssh/id_ed25519 ED25519 SHA256:1wgPtPehvxJHxq1qIDo4s7Eu1nZObhihxhAUBwbUHkU
Authenticated to servidor ([192.168.0.20]:22) using "publickey".   « 5. entrou
$

Leia sempre nessa ordem: rede (conectou?), servidor (a chave dele confere?), você (que chaves ofereceu, e qual foi aceita?).

2. Uma conexão que não deu

Aqui a chave do notebook não está no authorized_keys do servidor:

$ ssh -v -o BatchMode=yes lab@servidor true 2>&1 | grep -E 'Authentications that|Offering|Trying private key|Permission denied'
debug1: Authentications that can continue: publickey,password
debug1: Trying private key: /home/ana/.ssh/id_rsa
debug1: Trying private key: /home/ana/.ssh/id_ecdsa
debug1: Trying private key: /home/ana/.ssh/id_ecdsa_sk
debug1: Offering public key: /home/ana/.ssh/id_ed25519 ED25519 SHA256:1wgPtPehvxJHxq1qIDo4s7Eu1nZObhihxhAUBwbUHkU   « a chave foi oferecida...
debug1: Authentications that can continue: publickey,password
debug1: Trying private key: /home/ana/.ssh/id_ed25519_sk
debug1: Trying private key: /home/ana/.ssh/id_xmss
lab@servidor: Permission denied (publickey,password).   « ...mas o servidor não a conhece
$

O servidor recusou a chave oferecida e só sobrou a senha. A conclusão: o problema é o authorized_keys do servidor, não a rede.

3. O que o ssh vai fazer, sem conectar

O ssh -G (do Nível 3) mostra a configuração calculada: útil quando a dúvida é o ~/.ssh/config.

$ ssh -G interno | grep -E '^(hostname|user|port|proxyjump|identityfile) '
user lab
hostname 192.168.0.130
port 22
identityfile ~/.ssh/id_rsa
identityfile ~/.ssh/id_ecdsa
identityfile ~/.ssh/id_ecdsa_sk
identityfile ~/.ssh/id_ed25519
identityfile ~/.ssh/id_ed25519_sk
identityfile ~/.ssh/id_xmss
proxyjump servidor
$
Do lado do servidor

Quem tem acesso ao servidor pode olhar o log (aula dos logs), que às vezes diz o motivo exato, como bad ownership or modes. Em último caso, sudo /usr/sbin/sshd -d -p 2222 sobe um sshd de teste que atende uma conexão na porta 2222 e explica tudo na tela.

Quando dá errado

Parou no passo 2

Num notebook que ainda não conhece o servidor, com BatchMode=yes (sem perguntas), o -v mostra que a conexão nem chegou à sua chave:

$ ssh -v -o BatchMode=yes lab@servidor true 2>&1 | grep -E 'Connection established|Server host key|host key is known|verification failed'
debug1: Connection established.
debug1: Server host key: ssh-ed25519 SHA256:J0mxzl4IvFNcHQshs1EWMr0nqvoP4JTeJSyl7UkanuE
Host key verification failed.
$

A rede está boa (passo 1), mas a chave do servidor não pôde ser conferida (passo 2). Veja a aula de erros de host. Lembre: sem o 2>&1, as linhas do -v passam direto pelo grep.

Resumo

  • Rede, servidor, você: nessa ordem.
  • O -v sai pela saída de erro.
  • O log do servidor completa a história.
