Permissões do ~/.ssh

O SSH ignora arquivos que outros possam ler ou alterar. Esta aula mostra as permissões certas e o que acontece com as erradas.

Você vai aprender
  • As permissões certas de cada arquivo.
  • O aviso UNPROTECTED PRIVATE KEY FILE.
  • O StrictModes do servidor e o log dele.

Todas as saídas desta aula foram colhidas de verdade com o OpenSSH 10.0p2 no Linux (Debian 13, Bash 5.2, pt_BR.UTF-8), no laboratório do guia: o notebook (usuária ana, 192.168.0.10), o servidor (usuário lab, 192.168.0.20) e o interno (192.168.0.130, que só o servidor alcança). Antes de cada caixa o laboratório volta a um estado conhecido. As chaves e as impressões digitais que aparecem são de teste e já foram destruídas.

A ideia: o ssh confere quem pode ler e escrever

O SSH é desconfiado de propósito. Se a sua chave privada puder ser lida por outros usuários, ou se o authorized_keys do servidor puder ser alterado por outros, ele ignora o arquivo. As permissões certas:

ArquivoPermissãoPor quê
~/.ssh700 (drwx------)só você entra na pasta
~/.ssh/id_ed25519 (privada)600 (-rw-------)só você lê o segredo
~/.ssh/id_ed25519.pub644a pública pode ser lida
~/.ssh/authorized_keys, config600ninguém mais altera
a pasta pessoal (~) no servidorsem escrita para os outros (755 ou 700)senão, outro usuário poderia trocar o .ssh

1. Conferir

$ ls -ld ~/.ssh
drwx------ 2 ana ana 4096 nov 21 12:01 /home/ana/.ssh
$ stat -c '%a %U %n' ~/.ssh ~/.ssh/*
700 ana /home/ana/.ssh
600 ana /home/ana/.ssh/id_ed25519
644 ana /home/ana/.ssh/id_ed25519.pub
600 ana /home/ana/.ssh/known_hosts
$

2. Chave privada aberta demais

Alguém (ou um cp descuidado) deixou a chave com 644. O ssh se recusa a usá-la e cai para a senha:

$ ls -l ~/.ssh/id_ed25519
-rw-r--r-- 1 ana ana 399 nov 21 12:01 /home/ana/.ssh/id_ed25519
$ ssh lab@servidor hostname
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @   « chave legível por outros
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

It is required that your private key files are NOT accessible by others.
This private key will be ignored.
Load key "/home/ana/.ssh/id_ed25519": bad permissions   « o ssh ignorou a chave
lab@servidor's password:    « e caiu para a senha
servidor
$ chmod 600 ~/.ssh/id_ed25519
$ ssh lab@servidor hostname
servidor
$

3. Do lado do servidor: StrictModes

No servidor, o sshd faz a mesma conferência (opção StrictModes, ligada por padrão). Aqui, a pasta /home/lab ficou com escrita para todos (777). O cliente só vê a chave ser recusada; o motivo aparece no log do servidor. (O Debian e o Ubuntu toleram escrita para o grupo quando o grupo só tem o próprio usuário; escrita para todos, nunca.)

$ ls -ld /home/lab
drwxrwxrwx 4 lab lab 4096 nov 21 12:01 /home/lab   « qualquer um pode escrever: perigoso
$ sudo grep 'bad ownershi[p]' /var/log/auth.log
2026-11-21T12:01:58.407658-03:00 servidor sshd-session[51]: Authentication refused: bad ownership or modes for directory /home/lab   « o sshd recusou o authorized_keys
$

O [p] no fim do padrão é um truque: assim o grep não acha a linha que o próprio sudo grava no log com o comando. A correção é chmod 755 /home/lab (ou 700) no servidor.

Quando dá errado

Arrumar tudo de uma vez

Na dúvida, estes três comandos deixam a pasta do notebook como o ssh gosta:

$ chmod 700 ~/.ssh
$ chmod 600 ~/.ssh/id_ed25519 ~/.ssh/known_hosts
$ chmod 644 ~/.ssh/id_ed25519.pub
$ stat -c '%a %U %n' ~/.ssh ~/.ssh/*
700 ana /home/ana/.ssh
600 ana /home/ana/.ssh/id_ed25519
644 ana /home/ana/.ssh/id_ed25519.pub
600 ana /home/ana/.ssh/known_hosts
$

Do lado do servidor, o equivalente é chmod 700 ~/.ssh e chmod 600 ~/.ssh/authorized_keys.
