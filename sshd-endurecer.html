Endurecendo o servidor

Algumas linhas num arquivo só deixam o servidor bem mais fechado.

Você vai aprender
  • Montar um arquivo de endurecimento.
  • Conferir com sshd -T.
  • Trocar a porta e conectar nela.

Todas as saídas desta aula foram colhidas de verdade com o OpenSSH 10.0p2 no Linux (Debian 13, Bash 5.2, pt_BR.UTF-8), no laboratório do guia: o notebook (usuária ana, 192.168.0.10), o servidor (usuário lab, 192.168.0.20) e o interno (192.168.0.130, que só o servidor alcança). Antes de cada caixa o laboratório volta a um estado conhecido. As chaves e as impressões digitais que aparecem são de teste e já foram destruídas.

Um arquivo com o essencial

Juntando o que você viu, mais algumas opções, dá para guardar tudo num arquivo só. Cada linha:

LinhaO que faz
PasswordAuthentication nosó chave.
PermitRootLogin nonada de root direto.
KbdInteractiveAuthentication nofecha a outra porta de senha (já vem assim no Debian).
MaxAuthTries 3no máximo 3 tentativas por conexão.
AllowUsers labsó estes usuários entram, mais ninguém.
X11Forwarding nosem janelas gráficas pelo SSH.
Deixe uma sessão aberta

Antes de mexer no sshd de um servidor remoto, deixe um terminal conectado e teste a mudança em outro. Se a configuração nova trancar você do lado de fora, a sessão antiga ainda está lá para desfazer.

1. Escrevendo e recarregando

$ printf 'PasswordAuthentication no\nPermitRootLogin no\nKbdInteractiveAuthentication no\nMaxAuthTries 3\nAllowUsers lab\nX11Forwarding no\n' | sudo tee /etc/ssh/sshd_config.d/50-endurecer.conf
PasswordAuthentication no
PermitRootLogin no
KbdInteractiveAuthentication no
MaxAuthTries 3
AllowUsers lab
X11Forwarding no
$ sudo sshd -t && sudo kill -HUP "$(cat /run/sshd.pid)"
$
$ sudo sshd -T | grep -E '^(passwordauthentication|permitrootlogin|maxauthtries|allowusers|x11forwarding) '
maxauthtries 3
permitrootlogin no
passwordauthentication no
x11forwarding no   « o arquivo principal diz yes, mas o seu veio antes
allowusers lab
$

2. Testando do notebook

$ ssh lab@servidor hostname
servidor   « o lab, com chave, entra
$ ssh -o PubkeyAuthentication=no lab@servidor
lab@servidor: Permission denied (publickey).   « sem chave ou fora do AllowUsers, não
$ ssh -o BatchMode=yes ana@servidor hostname
ana@servidor: Permission denied (publickey).
$

3. E trocar a porta?

Mudar a porta 22 para outra (Port 2222) não deixa o servidor mais seguro de verdade, mas diminui muito o lixo nos logs. Quem conecta precisa do -p (ou do Port no config). A chave do servidor é a mesma, então o ssh não pergunta nada:

$ ssh -p 2222 lab@servidor hostname
servidor   « na porta nova, entra
$ ssh lab@servidor hostname
ssh: connect to host servidor port 22: Connection refused   « na 22, já não há ninguém
$
Firewall

Se o servidor tiver firewall (ufw, nftables, o painel do provedor), libere a porta nova antes de recarregar o sshd.

Quando dá errado

Usuário fora da lista

Com AllowUsers lab, até um usuário que existe e tem a senha certa fica de fora. No log do servidor aparece o motivo:

$ sudo grep 'not allowe[d]' /var/log/auth.log
2026-11-21T12:03:09.261193-03:00 servidor sshd-session[52]: User ana from 192.168.0.10 not allowed because not listed in AllowUsers
$

Esqueceu alguém? Acrescente o nome na mesma linha (AllowUsers lab maria) e recarregue.
