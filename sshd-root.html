O login do root

O root é o primeiro nome que os robôs tentam. O melhor é ele nem entrar por SSH.

  • Proibir o root.

O root e o SSH

O root existe em todo Linux, então é o primeiro nome que os robôs tentam. O padrão do OpenSSH é PermitRootLogin prohibit-password: o root pode entrar, mas só com chave. O mais comum é ir além e proibir de vez, entrando como um usuário comum e usando sudo.

1. Como está

$ sudo sshd -T | grep '^permitrootlogin'
permitrootlogin without-password   « o nome antigo de prohibit-password
$

No laboratório, a chave da ana foi posta também no /root/.ssh/authorized_keys do servidor. Com o padrão, ela entra como root:

$ ssh root@servidor 'whoami; hostname'
root   « entrou como root, com a chave
servidor
$

2. Proibindo

$ echo 'PermitRootLogin no' | sudo tee /etc/ssh/sshd_config.d/20-sem-root.conf
PermitRootLogin no
$ sudo sshd -t && sudo kill -HUP "$(cat /run/sshd.pid)"
$ sudo sshd -T | grep '^permitrootlogin'
permitrootlogin no   « agora vale
$

Do notebook, a mesma chave já não serve para o root. O BatchMode=yes faz o ssh desistir em vez de perguntar a senha:

$ ssh -o BatchMode=yes root@servidor hostname
root@servidor: Permission denied (publickey,password).   « root barrado
$ ssh lab@servidor 'sudo whoami'
root   « como lab, o sudo ainda chega no root
$
sudo sem senha?

No laboratório, o lab usa sudo sem senha para as aulas andarem. Num servidor de verdade o sudo pede a senha do usuário; para ele perguntar por SSH, use ssh -t lab@servidor 'sudo comando' (o -t dá um terminal para a pergunta).

Quando dá errado

Trancado do lado de fora

Se o root era o único jeito de entrar e você proibiu, o servidor recusa até a chave certa:

$ ssh root@servidor
root@servidor: Permission denied (publickey).
$

Por isso: crie antes um usuário comum com sudo, entre com ele numa segunda janela e só então proíba o root. Se trancar mesmo assim, só o console do provedor (ou o teclado do servidor) resolve.
