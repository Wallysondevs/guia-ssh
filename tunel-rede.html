Túnel até outra máquina

O destino do -L pode ser outra máquina, desde que o servidor a alcance.

Você vai aprender
  • Levar uma porta até outra máquina.
  • Entender qual trecho é criptografado.
  • Entrar por SSH através de um túnel.

Todas as saídas desta aula foram colhidas de verdade com o OpenSSH 10.0p2 no Linux (Debian 13, Bash 5.2, pt_BR.UTF-8), no laboratório do guia: o notebook (usuária ana, 192.168.0.10), o servidor (usuário lab, 192.168.0.20) e o interno (192.168.0.130, que só o servidor alcança). Antes de cada caixa o laboratório volta a um estado conhecido. As chaves e as impressões digitais que aparecem são de teste e já foram destruídas.

A ideia: o servidor como ponte

O destino do -L não precisa ser o próprio servidor: pode ser qualquer máquina que o servidor alcance. No laboratório, a máquina interno (192.168.0.130) tem uma wiki na porta 80, mas fica numa rede que o notebook não enxerga. O servidor enxerga.

1. O notebook não chega lá

$ curl -sS --max-time 3 http://192.168.0.130/
curl: (7) Failed to connect to 192.168.0.130 port 80 after 0 ms: Could not connect to server
$ ssh lab@servidor 'curl -s http://192.168.0.130/'
<h1>Wiki interna</h1><p>Só a rede interna enxerga esta página.</p>   « do servidor, abre
$

2. Pelo túnel

$ ssh -f -N -L 8081:192.168.0.130:80 lab@servidor
$ curl -s http://localhost:8081/
<h1>Wiki interna</h1><p>Só a rede interna enxerga esta página.</p>   « do notebook, pelo servidor
$

O caminho: notebook (porta 8081) → SSH criptografado até o servidor → o servidor abre uma conexão comum até 192.168.0.130:80. Esse último trecho, dentro da rede do servidor, não é criptografado pelo SSH.

3. Um túnel até o próprio SSH

O destino pode ser até outro servidor SSH. Aqui, a porta 2200 do notebook leva à porta 22 do interno, e o ssh entra por ela:

$ ssh -f -N -L 2200:192.168.0.130:22 lab@servidor
$ ssh -p 2200 -o HostKeyAlias=interno lab@localhost hostname
interno   « entrou no interno pelo túnel
$

O HostKeyAlias=interno diz ao ssh para conferir a chave como sendo a do interno, e não a de “localhost”. Para isso existe um jeito bem mais simples, o ProxyJump.

Quando dá errado

O servidor também não alcança

Se nem o servidor chega ao destino, o túnel abre, mas cada conexão falha lá na ponta. O ssh avisa no terminal em que o túnel foi aberto:

$ ssh -f -N -L 8082:192.168.0.140:80 lab@servidor
$ curl -sS --max-time 5 http://localhost:8082/
curl: (56) Recv failure: Conexão fechada pela outra ponta
$

“connect failed” vem do servidor: confira, nele, se o destino responde (ssh lab@servidor 'curl -s http://destino/').

Missões

Rode no seu laboratório (o seu notebook e o seu servidor de teste) e cole o que o terminal respondeu. O botão Conferir compara com o que a saída real precisa ter.

Missão: leve a porta 8082 do notebook até o painel do servidor (127.0.0.1:8080, visto de lá) e baixe a página.



ssh -f -N -L 8082:127.0.0.1:8080 lab@servidor && curl -s http://localhost:8082/

<h1>Painel do servidor</h1><p>Esta página só abre no próprio servidor (127.0.0.1:8080).</p>

Missão: abra um túnel da porta 2201 até a porta 22 do servidor e entre por ele.



ssh -f -N -L 2201:localhost:22 lab@servidor && ssh -p 2201 -o HostKeyAlias=servidor lab@localhost 'echo "pelo túnel: $(hostname)"'

Resumo

  • O servidor é a ponte.
  • Do servidor ao destino não há criptografia do SSH.
  • Para SSH em cadeia, prefira -J.
